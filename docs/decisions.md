# Решения по ТЗ LayoutPilot (ADR)

Документ фиксирует спорные решения, принятые при согласовании ТЗ v0.1 → v0.2.
Формат: вопрос, решение, обоснование, последствия. Нумерация соответствует §20 ТЗ и
резюме изменений.

**Статус:** принято, 2026-10-30. Пересмотр — только по итогам этапа 0 (спайки).

---

## ADR-001. Enter и Tab не являются триггерами автокоррекции

**Вопрос.** Может ли автокоррекция срабатывать по Enter, как в Punto Switcher?

**Решение.** Нет. Триггеры v1 — пробел и знаки пунктуации. Tab — опция профиля
`aggressive`, по умолчанию выключена. Enter не поддерживается и в планах.

**Почему.**
- Enter обрабатывается приложением раньше, чем мы успеваем что-либо сделать: сообщение
  уходит, форма сабмитится, команда выполняется. С read-only evdev перехватить Enter
  нельзя, а `EVIOCGRAB` — это полный прокси ввода с риском «залипания» клавиатуры.
- Tab конкурирует с автодополнением в IDE/терминале и с переходом фокуса в формах;
  исправление в этот момент почти всегда нежелательно.

**Последствия.** Слово, завершённое Enter, остаётся как есть — его можно исправить
хоткеем. Ограничение вынесено в README, troubleshooting, критерий приёмки №12 и §9.2.
Заодно снимается класс гонок «исправление после отправки».

## ADR-002. Layout state — отдельный компонент MVP

**Вопрос.** Где отслеживается активная раскладка/группа?

**Решение.** Отдельный крейт `layoutpilot-layoutstate` и требования FR-39/NFR-15:
событийные провайдеры для X11, KDE, GNOME, Sway, Hyprland; при недостоверности
авто-коррекция запрещена.

**Почему.** evdev даёт только физические keycode. Без текущей группы/keymap нормализация
в символы неверна, и «исправление» портит текст — это худший из возможных багов для
утилиты, которая правит чужой ввод. В v0.1 компонент был нарисован на схеме, но не
имел ни требований, ни провайдеров.

**Последствия.** +1 крейт, +1 таблица бэкендов, отдельный набор тестов (матрица смены
группы/устройства). В `doctor` выводится активный провайдер и его достоверность.

## ADR-003. LLM вне горячего пути

**Вопрос.** Может ли локальный LLM разрешать «серую зону» в момент разделителя?

**Решение.** Нет. Авто-путь детерминированный (словари + n-граммы + ONNX). LLM — только
ручной запрос, асинхронная подсказка в серой зоне и офлайн-пересчёт приоритетов обучения.

**Почему.** Коррекция выполняется сразу после разделителя; если ждать арбитра 300 мс,
пользователь уже напечатает дальше, и «отменить N и перепечатать» задним числом сломает
текст. Кроме того, ожидание в горячем пути убивает NFR-01 и делает поведение
недетерминированным для тестов.

**Последствия.** NFR-02 переформулирован; §9.3 переписан; FR-21/23 уточнены. Подсказка
показывается уведомлением и текст сама не меняет.

## ADR-004. Честная формулировка приватности; strict_capture — v2

**Вопрос.** Можно ли обещать, что демон «не видит» нажатия в blacklist-приложениях?

**Решение.** Нет. Обещание: «не обрабатываем и не сохраняем». Буфер чистится при смене
фокуса, входе в blacklist, паузе, блокировке экрана и таймауте. `EVIOCGRAB` + проксирование
(`strict_capture`) — только v2, opt-in, с watchdog.

**Почему.** evdev читается до того, как известен фокус; пароль успевает попасть в буфер.
Технически «не видеть» можно лишь полным перехватом устройства, а это риск зависшего
ввода при падении демона — недопустимо по умолчанию.

**Последствия.** README и `docs/privacy.md` содержат прямое признание; FR-14 и §12.1
переписаны; добавлен риск «залипание ввода».

## ADR-005. GNOME: базовая поддержка в v1, extension в v1.x

**Вопрос.** Делать ли GNOME-расширение Shell в v1?

**Решение.** Нет. В v1: захват, EIS-инъекция, переключение раскладки через gsettings,
`app_id` best-effort через AT-SPI. Per-window и надёжный focus — v1.x, отдельный пакет.

**Почему.** Расширение — второй язык (JS), отдельный цикл ревью на extensions.gnome.org,
поддержка версий Shell каждые ~6 месяцев. Оно не должно блокировать вертикальный срез,
а AT-SPI даёт достаточный `app_id` для blacklist у большинства приложений.

**Последствия.** Критерий приёмки №1 и матрица совместимости говорят «GNOME — базовая
поддержка, per-window не заявлен». При неопределённом `app_id` — консервативный режим.

## ADR-006. Порядок инжекторов: EIS → virtual-keyboard → uinput → clipboard

**Вопрос.** Какой инжектор основной на Wayland?

**Решение.**
- X11: XTest → clipboard.
- GNOME 46+/KDE 6+: EIS/libei.
- wlroots (Sway/Hyprland): virtual-keyboard-v1.
- Далее: uinput (в играх запрещён по умолчанию) → clipboard.

**Почему.** EIS передаёт keycode в evdev-семантике, композитор транслирует его своим
keymap — приём «переиграть те же физические клавиши» работает, и нет проблем per-device
раскладки. uinput создаёт новое устройство: в wlroots/KDE раскладка может быть
per-device, устройство видно античитам, в играх с raw input поведение иное.

**Последствия.** §8.2 переписан, добавлено правило «ровно один активный инжектор»,
capability detection в `doctor`, флаг `allow_uinput_in_games = false`.

## ADR-007. Клавиатурная обратимость как условие авто-исправления

**Вопрос.** Что делать, если исправленная строка содержит символы, которых нет на клавишах?

**Решение.** В авто-режиме такие строки не исправляются. В ручном (выделение/хоткей) —
Unicode-инъекция с подтверждением.

**Почему.** Приём «повторить те же клавиши» работает только для символов, маппящихся на
(keycode, модификаторы). Иначе получится не тот текст, а «полуисправленное» состояние хуже
исходного.

**Последствия.** FR-38, шаг 7 конвейера, §9.5. Добавлен property-тест «необратимая строка
не исправляется».

## ADR-008. Сброс контекста при смене фокуса и действиях указателя

**Вопрос.** Сбрасывать ли буфер по клику, скроллу, Alt+Tab, блокировке экрана?

**Решение.** Да, всегда (FR-40). Смена раскладки и устройства — тоже граница слова.

**Почему.** «Последнее слово» после клика мышью в другое место — уже не то слово. Это
самый частый источник заметных ложных срабатываний, дешевле предотвратить, чем ловить.

**Последствия.** Новый FR, пункт в §9.2, тесты на сброс; стоимость — один сброс состояния
на событие, в бюджет p99 не влияет.

## ADR-009. Ограничения undo

**Вопрос.** Работает ли undo после того, как пользователь продолжил печатать?

**Решение.** Нет. Undo доступен, только если после коррекции не было ввода и не менялись
фокус/layout state. Иначе — no-op и уведомление.

**Почему.** `Backspace × N` удалит уже чужой текст. Молчаливая порча текста недопустима.

**Последствия.** FR-04, §9.4; тест «undo после ввода — no-op».

## ADR-010. IME: coexistence, а не борьба

**Вопрос.** Что делать при активном fcitx5/ibus?

**Решение.** Авто-коррекция выключена по умолчанию (`ime.disable_auto_when_active = true`),
ручной режим работает. Детект компоузинга на Wayland без IME-интеграции невозможен —
это задокументировано.

**Почему.** Вмешательство в преedit ломает ввод, а определить компоузинг по evdev нельзя.

**Последствия.** FR-08, §9.2, отдельный риск в §19.

## ADR-011. Popup вариантов без привязки к каретке

**Вопрос.** Показывать варианты рядом с курсором?

**Решение.** В v1 — фиксированный popup или пункт трея. Привязка к каретке — C, через
AT-SPI, если окажется надёжной.

**Почему.** Стандартного Wayland-протокола координат каретки нет.

**Последствия.** FR-05 переформулирован; UI-требование не блокирует v1.

## ADR-012. Калиброванная вероятность вместо margin в конфиге

**Вопрос.** Что означает `confidence_threshold = 0.85`?

**Решение.** В конфиге — вероятность `p ∈ [0,1]`, калиброванная на корпусе; внутренний
порог `θ = logit(p)`. По умолчанию `0.97`.

**Почему.** Margin в лог-пространстве не имеет пользовательского смысла и зависит от
масштаба признаков; вероятность можно осмысленно двигать и проверять.

**Последствия.** §10, §9.1 шаг 9; калибровка входит в этап 3 (Smart).

## ADR-013. Раздельные метрики precision и recall

**Вопрос.** Достижимы ли одновременно precision ≥ 0.98 и recall ≥ 0.95?

**Решение.** Нет, не одновременно и не на одном режиме. Цели: precision ≥ 0.99 на
авто-пути; recall ≥ 0.90 авто и ≥ 0.95 с хоткеем; FP ≤ 0.3%. Два корпуса — синтетический
и реальный (с согласия).

**Почему.** Консервативные пороги и правило «не уверен — не трогай» по определению
снижают recall. Смешивать авто и ручной режимы в одной цифре — самообман.

**Последствия.** NFR-06/07, §14.3, критерий приёмки №7.

## ADR-014. Бюджеты памяти и размера

**Вопрос.** Реалистичны ли 80 МБ RSS и 15 МБ бинарник?

**Решение.** Демон ≤ 60 МБ с ONNX (цель — `tract`), бинарник ≤ 20 МБ при динамической
линковке; GUI и LLM — отдельные бинарники. Бюджеты перепроверить на этапе 0.

**Почему.** ONNX Runtime сам по себе даёт 30+ МБ RSS; статическая линковка с ort/llama.cpp
в 15 МБ не укладывается.

**Последствия.** NFR-03/14; в §7.4 `tract` указан первым.

## ADR-015. Словари — отдельные пакеты со своей лицензией

**Вопрос.** Как совместить MIT/Apache-код с данными под CC BY-SA/GPL?

**Решение.** Код — MIT/Apache-2.0; словари — пакеты `layoutpilot-dict-*` с собственной
лицензией и атрибуцией; генерация из FrequencyWords (MIT) / Wiktionary (CC BY-SA) с
фиксацией версии и хэша.

**Почему.** Встраивание GPL-словарей XNeur в MIT-код — юридическая мина; ShareAlike для
данных требует отдельных условий распространения.

**Последствия.** §15, FR-16; лицензионная проверка — обязательный пункт релизного чек-листа.

## ADR-016. Сроки и границы MVP

**Вопрос.** Реалистичны ли 4–5 месяцев на весь scope и 5–7 недель на MVP?

**Решение.** MVP — 8–10 недель (один вертикальный срез: ядро + layout state + X11/evdev +
ru↔en + автокоррекция + хоткей + undo + CLI + тесты). Весь v1.0 — 6–8 месяцев соло.
GNOME extension — v1.x, strict_capture и облачный LLM — v2.

**Почему.** В v0.1 MVP включал ещё и Wayland-инъекцию, которой в плане отдельный этап;
оценки не сходились с содержанием.

**Последствия.** §17 и §18 обновлены; при появлении второго разработчика сроки
пересматриваются, а не scope.
